# Password recovery design

Requested: validate forgot email, lookup account privately, generate expiring reset token, email a reset link, limit requests, and validate/hash/consume reset once with old sessions revoked. User selected SMTP via environment and Mailpit for local. Existing account policy already revokes all access/refresh sessions after password changes; apply it to reset too.

Reuse current CUSTOMER account scope, password rules, token_version and user-first lock ordering. Fifteen-minute random token stored only as hash, invalidate old links on new accepted request. Email and source-IP throttles apply regardless of account existence; same forgot200 message for missing/blocked/noncustomer/throttled. Reset error400 hides invalid/expired/used states; independent IP429 protects reset attempts. Limits are configurable and rate transactions commit independently of reset failure.

SMTP dispatch runs after token commit through a bounded memory executor, never inside user/token locks. Only memory and outgoing email contain plaintext token; no DB outbox with raw tokens. Tradeoff: dispatch is not durable across process crashes; failed/queued-out email requires another request after cooldown. Configured trusted reset URL (HTTPS or loopback HTTP) uses fragment token; minimal same-origin backend form supports local flow and removes token from browser URL before submitting. Future FE can override URL.

Refinement: account lookup and token issuance run in the worker too, keeping API work independent of account eligibility. The facade holds no DB transaction while rate transactions execute; only the consumer owns the user/token transaction. Queue jobs carry a quota-window/sequence receipt checked under the user lock so delayed older accepted jobs cannot supersede newer requests. Timestamp storage uses direct JDBC LocalDateTime binding with UTC Clock to align expiry and native cleanup under the existing global Hibernate time-zone setting.

Reset locks user then token, checks active customer, expiry/revocation/use and original token version, validates new password and confirmation, saves hash, consumes token, invalidates other reset links and all sessions in one transaction. No automatic login. No changes to order/address snapshots or local-profile preference.
