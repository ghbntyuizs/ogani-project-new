# Forgot/reset password — SMTP and Mailpit

## API contract

Public `POST /api/auth/forgot-password`, no bearer token required:

```json
{"email":"eleanor@example.com"}
```

Validate a string email, normalized with trim/lowercase, maximum150 characters; reject missing/null/blank/invalid/wrong-type/extra fields with400. For a valid email, always200 with `If this email is eligible, a password reset link will be sent` and null data. The same response covers active/missing/blocked/noncustomer accounts, rate limiting, queue saturation and SMTP failure. This recovery feature is for active CUSTOMER accounts; Admin/Staff recovery is excluded. No token or email/account details are returned.

Default limits:3 accepted requests/email per15 minutes with60-second cooldown;20 requests/IP per15 minutes. Limits apply to unknown emails too. Requests above these limits silently receive the same200. Source is servlet remote address; unverified client X-Forwarded-For is not used. Configure trusted proxy forwarding deliberately if deployed behind a proxy. Account lookup, token creation and SMTP run in bounded background workers, so SMTP/eligibility work is outside response timing.

Public `POST /api/auth/reset-password`:

```json
{"token":"<43-character token from the email>","newPassword":"NewPassword123!","confirmPassword":"NewPassword123!"}
```

Required string fields only. Token is a random32-byte base64url value, generated by BE, not manually created by customer/FE. New password follows the existing policy:6+ characters and maximum72 UTF-8 bytes, nonblank, exact confirmation and different from current password; no trimming. Invalid input400. Unknown/expired/used/revoked token, blocked/noncustomer user or token invalidated by a password change all receive generic400 `Reset token is invalid or expired`. Same-password or mismatched/overlong password failures do not consume the token. Reset attempts with valid request shape are limited to50/IP per15 minutes, then429, even when token validation later fails.

Success200 has null data, no password/hash or new auth tokens. It stores a BCrypt hash, marks the reset token used and revokes every other pending link and all access/refresh sessions atomically. Customer must sign in with the new password. A used link cannot be reused. Existing order/address/profile data is unchanged. Existing password-change API invalidates outstanding issued links through the shared user token version.

## Local Mailpit test

From repository root, with Docker available:

```powershell
docker compose -f backend/docker-compose.yml --profile mail up -d mailpit
```

Mailpit UI: `http://localhost:8025`; SMTP: `localhost:1025`. Ports are bound to127.0.0.1 in Compose. Mailpit captures emails locally instead of sending them to real inboxes. Docker is not installed in the current inspected environment, so this service was not launched here. A Windows standalone binary is another option in [Mailpit installation instructions](https://mailpit.axllent.org/docs/install/); bind it to loopback for local development.

1. Start Mailpit, then run backend in IntelliJ as usual (local profile). Defaults use localhost:1025 without SMTP auth/TLS and sender no-reply@ogani.local.
2. In Swagger, call forgot-password with an existing active CUSTOMER email. No login or manual token generation is needed.
3. Open Mailpit UI, open the captured email and click its reset link. Default link goes to backend `/reset-password.html#token=...`, which is public and works without the missing storefront.
4. Enter matching new passwords and submit. The page removes the fragment from the visible URL, keeps the token only in memory, and asks you to return to the application and log in on success. Refreshing this page loses the token; reopen the original email link if needed.
5. Verify login succeeds with the new password; old access/refresh tokens fail. Reusing the link fails. To test expiry, wait15 minutes from issuance, or configure a shorter valid RESET_TTL_MINUTES before backend startup.
6. Alternatively, copy the43-character token after `#token=` into Swagger reset-password. It is delivered only via email, never by the forgot API response.

The reset form is intentionally minimal; customer storefront recovery screens remain outside this backend task. To host your own FE page, set PASSWORD_RESET_URL to its absolute HTTPS URL, read token from the fragment, send reset requests to the backend API origin and configure CORS_ORIGINS for that FE origin. Plain HTTP is accepted only for loopback. URL query, fragment and userinfo in configured base URL are rejected; request Host never determines the email link.

## SMTP environment

For a real SMTP server, configure these in the application's IntelliJ environment variables or process environment:

```text
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=your-smtp-user
SMTP_PASSWORD=your-smtp-password
SMTP_AUTH=true
SMTP_STARTTLS=true
SMTP_SSL=false
SMTP_FROM=no-reply@example.com
PASSWORD_RESET_URL=https://shop.example.com/reset-password.html
```

For implicit TLS, use the provider's port/SMTP_SSL settings instead of STARTTLS. No real credentials are checked in. Sending uses Spring Mail with5-second connection,3-second read and5-second write timeouts; see [Spring Boot email configuration](https://docs.spring.io/spring-boot/reference/io/email.html).

Other optional variables: RESET_TTL_MINUTES=15, RESET_EMAIL_LIMIT=3, RESET_IP_LIMIT=20, RESET_ATTEMPT_LIMIT=50, RESET_WINDOW_MINUTES=15, RESET_COOLDOWN_SECONDS=60. Values are startup-validated. In Docker app mode, default SMTP_HOST is mailpit; start the mail profile together with app/db. Existing local profile and JWT configuration are preserved.

## Storage, locking and delivery tradeoff

V15 adds password_reset_tokens and hashed rate-limit buckets with lookup/cleanup indexes. Only SHA-256 token hashes are stored; reset DTO/delivery toString is redacted and application failure logs omit email, link and raw token. Token timestamps are UTC wall-clock values bound through direct LocalDateTime JDBC mapping, avoiding the pre-existing global UTC calendar/JVM timezone conversion. Expiry is checked after locks, with an exclusive boundary.

All credential writers take user before reset/refresh token locks. Rate consumption commits in its own transaction before the consumer transaction, so failed token attempts still count. The nontransactional facade avoids nested connection-pool exhaustion. Reset token use, password hash, user version and all refresh revocations roll back together on a late database error.

Queue work carries the email quota receipt (window+sequence), checked after taking the user lock. Older accepted jobs that were delayed are skipped if superseded, so they cannot invalidate the newest request's link. A newly issued link invalidates older issued links. SMTP runs only after issuer commit; pool2/queue50 bounds in-memory work. Delivery is not durable across crashes or SMTP failures; the caller still receives the generic response and can request again after cooldown/limits permit. No plaintext-token database outbox or automatic SMTP retries are included. Mailpit was configured, but no external provider inbox delivery is claimed.

Hourly maintenance removes at most1000 token rows expired over24 hours and1000 rate buckets older than24 hours per run, using skip-locked batches. Active tokens are preserved. Forgot/token mechanisms follow the security practices in [OWASP password recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
